# 失败处理与跨轮恢复

## 失败分类

| 类 | 现象 | 动作 |
|---|---|---|
| **局部** | `agent()` 返回 `null`；工具调用失败；输出不合 schema | 补上下文重试 1 次；仍失败按 criticality 处理 |
| **上游** | 产出引用了不存在的文件/接口；verifier 指出"缺输入" | 退回上游那条重跑，把 issue 原文带进去 |
| **结构** | ≥2 个并行任务同一原因失败；契约自相矛盾；重试 2 次仍不过 | 停止扇出，回 Plan 重拆；必要时交人 |

criticality 快速判：影响交付 → critical；影响局部完整性 → normal；可省略 → optional。`optional` 失败直接跳过并在结果里标注。

## 重试预算

| 动作 | 上限 | 到顶后 |
|---|---|---|
| 单任务重跑 | 2 次 | 交人，附两次失败原因 |
| 回退上游修正 | 2 跳 | 判定为结构问题，回 Plan |
| 整轮 workflow 重跑 | 1 次 | 换拆法或缩小范围，不要原样再跑 |

**不要指数退避式硬重试。** Agent 失败多因信息缺失或任务过大，重复调用只是重复失败。每次重试必须改变输入：补上下文、缩小范围、换角色。

## 结果不完整时怎么交付

- 明确写：完成 X/Y，失败项列表 + 原因。
- 已完成部分的产物照常交付，不要因为 2 个失败把 8 个成功藏起来。
- 给用户可执行的下一步：重跑哪几条、需要什么信息。
- 绝不用"已完成"掩盖缺失——用户按这个结论做决策，比失败更贵。

## 跨轮恢复

只有任务确实要跨多轮（超过一次对话能完成、或用户中途离开）时才落盘，不要为一次性任务建状态文件。

位置：`./.orchestrate/<slug>/state.json`（工作目录内，随项目走）

```json
{
  "goal": "给订单服务加幂等键",
  "updated_at": "2026-10-20T23:50:00+08:00",
  "phase": "implement",
  "tasks": [
    { "id": "schema", "status": "done", "artifact": "db/migrations/003.sql" },
    { "id": "api", "status": "done", "artifact": "src/orders/idempotency.ts" },
    { "id": "tests", "status": "failed", "error": "缺少 redis 测试容器" }
  ],
  "next": "为 tests 提供 redis 容器或改用内存实现后重跑"
}
```

规则：
- 每轮结束写一次（不是一个任务写一次）。
- 恢复时先读 `next`，只重跑 `pending`/`failed`，`done` 直接复用产物。
- 同时用 `create_goal` 锚定总目标；`update_goal` 只在阶段完成时调用。
- 任务完成或放弃时删掉该目录，避免下一轮误恢复。

## 成本护栏

| 信号 | 动作 |
|---|---|
| 预估 >10 个 Agent | 开工前告知用户，给"简化版/完整版"两个选项 |
| 单次 workflow >20 个 Agent | 拆成多次调用，中间落盘 |
| 实际耗时 > 预估 3 倍 | 中断，报告已完成部分，问是否继续 |
| 同一产物被退回第 3 次 | 停止，把两份判决一起交人判断标准是否错了 |
| Agent 输出显著超过预期体量（>3x） | 检查是否理解偏了，先停再决定是否拆 |

## 什么情况直接交人

- 需求本身自相矛盾，且用户没给优先级。
- 涉及不可逆操作（删数据、发布、改生产配置）。
- 两次结构性问题（拆法都不对）。
- 成本已超用户预期且未获确认。
